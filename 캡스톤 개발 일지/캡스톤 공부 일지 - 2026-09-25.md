## 개발 일지 & TIL

**퀘스트 제출 버튼과 완료 안내, Fetch 보상 검증**

[[00_캡스톤 제작 기록 - 2026년 9월~11월|← 날짜별 제작 기록 목차]]

### 기본 정보

- 날짜: 2026-09-25 (한국시간)
- 프로젝트: Starizon Light / GameCapstone
- 기록 성격: 구현·사용자 거래 확인

### 오늘 한 작업

- 재대화가 자동으로 거래를 완료하던 흐름을 제거하고 SubmitAcceptedQuest API를 추가했다. 입항 여부, 화면 방문 번호, QuestID, 수락 상태를 검증한 뒤 기존 GI 거래를 호출한다.
- bQuestSubmissionInProgress로 제출 중 재진입을 막고, 실패 사유를 반환하며, 성공 시 Completed 상태와 완료 구조체를 전달하도록 했다.
- WBP_QuestProposal1의 SubmitButton 클릭을 새 API에 연결하고, 성공 시 RefreshDialogue, 실패 시 RefreshDialogue 후 FailReason을 표시하도록 배선을 정리했다.
- 완료 후 빈 퀘스트 경로에서 Completed 상태를 검사하도록 실행선을 수정하고, 수락·제안·완료 상태별 버튼과 안내 문구를 분리했다.
- 실제 Fetch 제출 로그와 사용자 완료 후 재대화 확인 결과를 문서에 반영했다.

### 발생한 문제 & 대응

- 물품을 갖고 상인과 재대화하기만 해도 거래가 끝나 수락·완료 안내가 혼재했다. 조회와 명시적 제출을 분리했다.
- 제출 후 '현재 표시할 퀘스트가 없습니다'가 나온 원인은 Completed 검사 실행선이 Proposed 경로에 연결된 배선이었다. 빈 퀘스트 경로의 SubmitButton 숨김 뒤로 옮겼다.

### 확인 결과와 검증 범위

- 사용자 PIE 로그에서 Debug_AddItem으로 Wheat 17개 준비 → 제출 → Wheat 17→0, gold 0→136을 확인했다. 해당 Submitted 성공 로그는 1회이며 상인 재고의 거래 후 Wheat 20이 기록됐다.
- 사용자가 '완료하고 말을 걸면 완료 문구가 유지되'라고 확인했다. 같은 입항 중 재대화 UI 유지 범위다.
- Loading model/503 후 1회 재시도와 템플릿 생성도 확인했다. 전체 빌드 식별자·로그는 제공되지 않았고 AI 빌드·PIE는 없었다.

### 당시 남은 문제 / 미확인 사항

- 상인 재고의 정확한 거래 전후 차이, 부족 조건, Sell, 중복 클릭, 출항·재입항 후 오래된 화면, 디스크 저장·재실행 복원은 당시 미검증이었다.
- 디버그 아이템 지급은 필드 획득부터 제출까지의 일반 플레이 루프 검증을 대신하지 않는다.

### 다음 작업 — 당시 기준

- 요구량보다 1개 부족한 Fetch를 제출해 실패 이유·Accepted 유지·잔고 불변을 확인한 뒤 보충 후 성공을 확인한다.
- Sell 거래, 중복 제출과 UI 종료 후 조작 복귀, 저장·복원을 순서대로 시험한다.

### 오늘의 기술 정리 (TIL)

- UI 새로고침 후 실패 이유를 표시해야 일반 대사가 오류 문구를 덮어쓰지 않는다.
- 완료 뒤 GetCurrentQuest가 빈 구조체를 반환하면 퀘스트 데이터가 아니라 상인의 OfferState로 완료 안내를 결정한다.
- GI.TryCompleteQuest를 UI에서 직접 호출하면 상인 재고 후처리를 우회할 수 있으므로 상인의 제출 API를 사용한다.
