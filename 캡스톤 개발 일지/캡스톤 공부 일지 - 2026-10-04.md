## 개발 일지 & TIL

**거래·재고 저장 검증, ESC 인벤토리와 해상 회수 계획**

### 기본 정보

- 날짜: 2026-10-04 (한국시간)
- 프로젝트: Starizon Light / GameCapstone
- 기록 성격: 사용자 저장·복원 확인·UI·설계

### 오늘 한 작업

- **코드 구현** — GameInstance가 OnInventoryChanged를 구독해 메인맵 변경을 dirty로 표시하고, 같은 프레임의 저장 요청을 다음 틱 한 번으로 합치도록 했다.
- **거래 일관성** — BeginProgressUpdate/EndProgressUpdate 범위 동안 쓰기를 미뤄 아이템·골드·경험치·퀘스트·상인 상태를 거래 처리 완료 뒤 같은 스냅샷으로 저장하게 했다.
- **복원 보호** — 로드·새 게임 적용 중 알림의 재저장, 과거 예약의 저장 파일 재생성, 항구 복귀 전 저장을 막는 가드를 넣었다. 쓰기 실패 시 dirty와 오류를 유지하고 명시 재시도 API를 제공했다.
- **코드 구현** — FMerchantStockSaveData와 MerchantID별 재고/LastRestockDay 저장 맵, GI의 복원·기록 캐시를 추가했다. 플레이어 상태와 같은 SaveObj에 상인 상태를 기록한다.
- **구형 저장 호환** — 상인 기록이 없는 기존 저장은 안내 후 배치 초기 재고로 시작하고 플레이어 진행은 유지한다. 과거 상인 재고를 추정하지 않았다.
- ESC 인벤토리의 ItemIconMap, 표시명·수량, 정사각형 슬롯과 UniformGrid 배치를 연결했다. gold·수량 0 이하를 아이템 칸에서 제외하고 SlotIndex/3·SlotIndex%3으로 배치하도록 수정했다.
- 컨트롤러의 ESC 앞단에서 퀘스트 창 존재 여부를 검사해 먼저 CloseDialogue만 실행하고, 퀘스트 창이 없을 때 인벤토리를 토글하도록 정리했다.
- 배로 접근해 상호작용 키를 누르면 통/박스 내용물이 기존 InventorySubsystem에 들어오는 획득 방향을 정리했다.
- 퀘스트 수락→출항→부유물 회수→귀항/제출→보상→다음 항해의 최소 반복 흐름을 계획했다.
- 기존 배 IA_Interact가 하선에 사용됨을 확인하고, 통이 있을 때 회수 우선·없을 때 하선하는 입력 분기 및 중복 지급 방지를 설계했다.
- 10월5일 작업 계획을 기록했다. 계획 작성일은 10월4일이며 이 단계에서 통 코드나 에셋을 구현하지 않았다.

### 발생한 문제 & 대응

- 아이템을 추가한 뒤 저장 호출 없이 종료해 이어하기 수량이 0이 됐다. 저장 배열 누락이 아니라 변경 후 저장 요청 부재로 확인됐다.
- 플레이어 납품 결과는 복원되는데 상인 재고만 초기화돼 같은 요구량·보상이 반복됐다. 상인 재고와 재입고 날짜의 저장 누락을 보완했다.
- 아이템 슬롯이 겹쳐 보이던 그래프에는 %1과 SlotIndex 증가 누락이 있었다. %3과 추가 후 증가를 안내한 뒤 나란히 표시된다는 사용자 확인을 받았다.
- 퀘스트 창 위에 ESC 인벤토리가 열리고 인벤토리를 닫으면 대화창 입력도 막히는 문제가 있었다. Length>0→Branch Condition, True→CloseDialogue 실행선과 ESC 우선순위를 연결했다.
- 선박 UI에 ShipRank 기본 문구·내구도 0/0과 Accessed None이 나타났으며 실제 배 참조와 CombatComponent 유효성 확인이 남아 있었다.
- 현재 확인한 함포 발사 경로에는 인벤토리 포탄 차감·부족 시 차단이 없었다.

### 확인 결과와 검증 범위

- **사용자 로그 확인** — Debug_AddItem Wheat 200→자동 저장→종료→이어하기 후 Wheat x200과 ActiveQuests=1이 유지됐다. 재입항이나 퀘스트 제출 없이 아이템 변경 저장이 동작한 사례다.
- **사용자 로그 확인** — 플레이어 Wheat 166/gold 272에서 Wheat 17 납품·gold 136 수령 후 Wheat 149/gold 408/ActiveQuests=0으로 저장됐다. 상인 Wheat는 3→20, Cloth는 2로 유지됐다.
- **사용자 로그 확인** — 종료 후 Load Kingdom/PortRestore Restored와 재저장에서 플레이어 Wheat149/gold408, 상인 Day0/Cloth2/Wheat20이 그대로 보존됐다.
- **사용자 로그 확인** — 후속 제안에서 target_item_id=Cloth, target_amount=4가 나타나 복원된 재고를 따른 제안 변경 사례를 확인했다.
- **후속 근거** — 9월30일에 대기였던 Kingdom/Island1 항구 복귀 성공 로그가 10월4일 기록에서 확인됐다. 전체 저장 회귀가 통과했다는 뜻은 아니다.
- 사용자가 슬롯 나란히 표시와 기본 ESC 메뉴·커서 동작을 보고했고, 퀘스트/ESC 우선순위 수정·조작 복귀 항목을 인용해 '이건 했어'라고 확인했다.

### 당시 남은 문제 / 미확인 사항

- Sell, 날짜 증가·미로드 기간 재입고, 새 게임, 쓰기 실패·재시도, 중복 제출, 패키징은 별도 검증 대기였다.
- 메인 목표 단계와 방문·제안 UI 상태는 저장 범위에 포함하지 않았다.
- 다음 틱 전에 강제 종료하면 변경이 미저장일 수 있어 정상 종료·메뉴 이동 전 저장 완료 처리는 후속이었다.
- 마지막 ActiveQuests=1은 새 제안 이후 기록이며 천 퀘스트 ID·보상·제출 결과가 없어 이전 밀 퀘스트의 중복 복원으로 단정하지 않았다.
- 42종 아이콘 전체, 4번째 다음 줄·긴 목록 스크롤, 열어 둔 UI의 변경 이벤트 갱신, 골드 표시, 배 내구도 None 참조·ShipRank·Cannonball 원점은 미완료 또는 미확인이다.
- 내용물 품목·수량, 회수 거리, 재생성·저장 정책은 당시 미정이었다.
- 속도 표시 숨김 적용은 확인되지 않았다.

### 다음 작업 — 당시 기준

- 천 4개 요구의 UI 보상액과 제출 후 차감·보상·상인 재고 증가·재실행 보존을 확인한다.
- Sell 재고 감소, 날짜 리필, 새 게임 초기화와 쓰기 실패 재시도 경로를 확장 시험한다.
- 통에서 얻은 물품으로 수락→출항→회수→귀항→제출→저장하는 일반 플레이를 연결한다.
- 골드 표시와 배 정보 UI를 확인한 뒤 단일 통 수동 배치·회수부터 구현하고, 디버그 지급 없이 의뢰를 끝내는 흐름을 시험한다.

### 오늘의 기술 정리 (TIL)

- 거래 중 여러 상태가 바뀌는 경우 변경 알림마다 즉시 저장하면 중간 상태가 기록될 수 있어 거래의 바깥 경계에서 저장을 모아야 한다.
- 플레이어 저장과 상인 저장을 따로 보면 이어하기 후 경제 상태가 어긋날 수 있다. 동일 스냅샷에 재고와 재입고 날짜를 함께 남긴다.
- 구형 저장에 없는 필드는 과거 상태를 추측하지 않고 초기값 및 명시적인 이행 로그로 처리한다.
- 같은 상호작용 입력으로 회수와 하선이 동시에 실행되지 않도록 우선순위를 설계해야 한다.
- 인벤토리 저장 성공과 월드 통의 소진 상태 저장은 별도 요구다.
