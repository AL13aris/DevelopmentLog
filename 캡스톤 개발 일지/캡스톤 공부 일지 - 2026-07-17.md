### 발생한 문제 & 해결 방법

### **문제 상황**
- `FTradeGoodData`에 화폐로 쓰는 `"gold"`와 이름이 겹치는 교역품 `"Gold"`(사치품)가 있었음
- 교역품 42종/카테고리 11개로, 이미 확정한 MVP 범위(6~8종)를 크게 초과함
- `BaseProduction`이 소수점(0.1~0.5)인 항목 10개가 있어 `int32` 캐스팅 시 0으로 잘림
- 서민규가 함선 Pawn을 두 개(`ASloopPawn`, `AShipPawn`) 만듦 — 어느 것을 정식으로 쓸지 불명확
- `AShipPawn`에 기획서에서 의도한 `UBuoyancyComponent`가 없음(체인지리스트엔 "부력 완료"라고 되어 있었으나 코드엔 없었음)-> 퍼포스 재업로드로 해결
- `AShipPawn` 생성자에 `AutoPossessPlayer = EAutoReceiveInput::Player0`가 있어, 6.1에서 설계한 "플레이어가 상호작용으로 배에 탑승" 구조와 충돌
- LLM 응답에서 `quest_text`가 계속 플레이스홀더(`"..."`), 지시문 복사, 숫자 반복(`"0101..."`, `"000..."`) 등으로 나옴
- `quest_type`을 LLM이 직접 고르게 하니, 대사 내용(예: "식량이 부족하다")과 실제 고른 타입(sell)이 서로 모순되는 경우 발생

### **해결 방법**
- 골드 이름 충돌 → 팀원에게 요청해 `Gold` → `GoldBar`로 즉시 수정 완료
- MVP 범위 초과 → 42종 중 6~8종만 우선 사용, 나머지는 스트레치 골로 보관하기로 결정
- `BaseProduction` 소수점 → 팀원에게 정수로 변경 요청 (반영 대기 중)
- 함선 중복 클래스 → `AShipPawn`을 정식 채택(기획서 6.2 함수명과 정확히 일치), `ASloopPawn`은 삭제/archive 권장
- 부력 미구현/`AutoPossessPlayer` 충돌 → 서민규에게 확인 요청 필요 사항으로 정리해 전달
- LLM 대사 품질 문제 → 근본 원인이 `/completion`(순수 텍스트 이어쓰기 모드)을 쓰고 있었기 때문이라고 판단, `/v1/chat/completions`(system/user 역할 분리 chat 모드)로 전환 — 전환 후 대사 품질이 확실히 개선됨
- GBNF 폭주 버그들 → `number`에 0으로 시작 방지 규칙, `ws`에 상한, `string`에 문자셋 제한(한글/영문/기본 문장부호만) 추가로 하나씩 해결
- `quest_type` 불일치 → LLM에게 판단을 맡기지 않고, 재고 수치 기준으로 코드(`DecideQuestParameters`)가 먼저 결정한 뒤 LLM은 `quest_text`(대사)만 생성하도록 재설계 방향 결정 (코드 적용은 내일)

### **배운 점**
- `/completion`과 `/v1/chat/completions`는 완전히 다른 동작 모드다 — 전자는 "다음 텍스트를 통계적으로 이어쓰기"이고, 후자만 모델이 학습한 instruction-following 모드가 제대로 발동한다. Instruction-tuned(`-it`) 모델은 반드시 후자로 호출해야 함
- GBNF는 "형식"은 강제할 수 있어도 "내용 품질"은 강제할 수 없다 — 형식이 뚫린 게 아니라 애초에 잘못된 모드로 호출한 게 근본 원인이었던 것처럼, 문제의 층위를 구분해서 봐야 함
- 이미 "보상은 LLM이 정하지 않는다"(5.6)는 원칙을 LLM 연동에 적용했었는데, 같은 원칙을 `quest_type`/`target_amount`에도 적용해야 한다는 걸 이번에 알게 됨 — LLM에게 판단이 아니라 "이미 정해진 것을 문장으로 표현하는 역할"만 맡기는 게 더 안정적

### 오늘 배운 점 (TIL)
### **알게 된 내용:**
- llama-server는 `/completion`과 `/v1/chat/completions`를 동시에 제공하며, 어느 것을 쓸지는 서버 실행 인자가 아니라 클라이언트가 호출하는 URL로 결정된다
- `/v1/chat/completions` 응답 구조(`choices[0].message.content`)는 `/completion`의 `content` 직속 필드와 다르므로 파싱 로직도 같이 바뀌어야 함
- GBNF에서 `*`(0개 이상)나 `+`(1개 이상)처럼 상한 없는 반복 기호는 모델이 반복 생성 패턴에 빠졌을 때 폭주를 막아주지 못한다 — 실전에서는 `{min,max}`로 상한을 항상 걸어야 안전함
- `repeat_penalty` 같은 생성 파라미터를 요청에 명시적으로 추가하면 모델의 반복 폭주 성향을 줄일 수 있음
### **헷갈렸던 점**
- GBNF 필드 순서를 바꾸면(quest_type을 앞으로) 오히려 결과가 나빠진 것 — 앞쪽에 배치된 필드일수록 모델이 "근거 없이 먼저 결론부터 내야 하는" 부담이 커진다는 걸 실험으로 확인함. 순서 조정만으로는 근본 해결이 안 되고, 판단 자체를 코드로 옮기는 게 맞다는 결론에 도달함
- 프롬프트에 필드명(`quest_text`)을 직접 언급하면 모델이 그 단어 자체를 설명하려 드는 경향이 있다는 것 — GBNF가 이미 강제하는 키 이름을 프롬프트에서 또 언급할 필요가 없다는 걸 알게 됨
