### 오늘 한 작업

- 팀원 수정 이후 낮아진 지형과 Ocean 수면 사이에 경계가 남는 현상을 점검했다. 스플라인 선·조절점 표시와 WaterZone·수면 마스킹 설정을 살폈다.
- Water Opacity Mask Offset 위치를 확인하고 조정하며 시각적으로 남은 경계가 줄어드는지 비교했다.
- 사용자가 LV_MainMap의 #7을 정상, #8·#9를 문제 버전으로 지정하고 Perforce의 이전 리비전 받기와 Undo 범위8~9 절차를 검토했다.
- 구역당 목표 통 수를12→4, 최소 간격을12→25m로 조정한 뒤 플레이어 주변200m 격자 구역의 생성·정리를 구현했다.
- 같은 항차에서는 회수한 통을 다시 만들지 않고, 입항 시 활성 통 제거·생성 중단 후 배가 모든 항구 영역을 벗어날 때 항차를 증가시켜 배치와 보상을 새로 생성하도록 했다.
- 처음150~400m 생성/600m 정리에서 최종 기본300~700m 생성/1000m 정리로 거리를 확대했다. 활성 통24개와 초당 생성 시도2회 상한을 유지했다.
- 화면 안600m 미만 후보를 보류하고 화면 밖 또는 충분히 먼 전방에서 등장하게 하는 카메라 기준 생성 규칙을 추가했다.
- 적 함선을 붙이기 전 CombatComponent·ShipBase·PlayerShipPawn의 사망 처리를 단일화하고 파괴 후 새 발사·조작·통 회수·승하선을 차단했다.
- 플레이어의 전투 레벨 명중률 보너스를 PlayerShipPawn override로 분리하고, 이미 비행 중인 포탄의 피해는 유지했다.
- **코드 구현** — Debug_PrintInventory Exec 명령을 PlayerCharacter에서 StarizonGameInstance로 옮겨 Pawn 종류에 관계없이 같은 InventorySubsystem을 읽도록 했다.
- **출력 개선** — 기존 품목·수량·교역품 로그를 유지하고 빈 목록에는 '(비어 있음)'을 출력하도록 했다. 데이터 자체는 변경하지 않는다.
- **경로 확인** — 로컬 UE5.7 GameViewportClient의 GameInstance Exec/ProcessConsoleExec 전달 경로를 확인해 별도 함선 전달 함수나 엔진 수정 없이 공통 명령을 연결했다.

### 발생한 문제 & 대응

- 지형 높이를 낮춘 뒤 물 경계가 생겼으며 스플라인을 당겨도 기대한 결과가 나오지 않았다.
- 수면의 시각적 마스크가 바뀌는 것과 부력이 작동하는 영역을 구분할 필요가 있었다.
- 통이 한 구역에 지나치게 몰려 보여 개수와 최소 간격을 함께 조절했다. 화면 가까이 갑자기 나타나는 느낌을 줄이기 위해 생성 거리를 늘렸다.
- 기존 전투 코드의 중복 파괴 호출, 유효하지 않은 피해값, 사망 콜백 재진입·BP Parent 누락, 발사 도중 사망에 따른 후속 포탄 생성 경로를 보완했다.
- 통 보상은 공유 인벤토리에 들어가 ESC UI에 보였지만, 배를 조종할 때 캐릭터 소유의 Debug_PrintInventory 콘솔 명령으로 확인하기 어려웠다.

### 확인 결과와 검증 범위

- 한국시간10월27일19:52 사용자가 '경계가 달라지긴 하네',19:56 '줄었어'라고 경계 변화·감소를 보고했다. 완전한 해안선 복구나 부력 복구를 확인한 결과는 아니다.
- 한국시간10월27일20:19 사용자가 '7번으로 일단 다운 받아놨어'라고 정상 리비전의 로컬 다운로드를 확인했다.
- 사용자가 원인을 찾았다고 말했으나 구체적인 원인은 해당 발화에 명시하지 않았다.
- 변경 전 설정에서 사용자 로그의 generated=12/12, Wheat0→10→18 지급과 Saved Inventory=[Wheat x18]을 확인했다. 사용자는 ESC 인벤토리 표시도 확인했다.
- 사용자가 '이제 좀 낫네'로 밀도 개선을, '잘 생성 되는거 확인했고'로 직전 주변 생성의 인게임 동작을 보고했다.
- 순수 시드·항차 로직107,584사례, 화면 확장 계산10,000사례와 독립 전투 회귀17개+발사중사망1개 검사를 수행했다. 모두 Unreal 물리/PIE 전체 검증과는 별개다.
- **정적 확인** — 명령 선언·정의, 단일 소유자와 콘솔 전달 경로를 점검했다.
- **미검증** — 이동 후의 명령을 보행·배 탑승 두 상태에서 실제 실행하는 시험과 재실행 로드는 기록상 대기였다.

### 당시 남은 문제 / 미확인 사항

- Undo 후 Submit 가능한지 질문한 것만 확인된다. 복원본 제출 성공·최신 리비전 생성·팀원 동기화 완료는 입증되지 않는다.
- 기존 #8·#9 이력 삭제나 서버 영구 제거를 수행·완료한 것으로 기록하지 않는다.
- Water 설정 변경의 정확한 최종 수치와 원인, 부력 영향은 확정하지 않는다.
- 항구 왕복 초기화·회수 소진 유지·Cloth·연타·새 거리/화면 규칙은 각각 사용자 런타임 재확인이 필요했다.
- 항차·소진 캐시는 실행 중 상태이고 저장 파일에 추가하지 않았다.
- 화면 기준 보류는 페이드/디더 연출이 아니다. 실제 액터 생성은 즉시 이루어진다.
- 전투 중 하선·입항 잠금, 플레이어 패배·리스폰, 적 AI 추격/복귀/회복은 아직 구현하지 않았다.
- 명령 이동의 정적 확인을 보행·탑승 PIE 성공으로 간주하지 않는다.

- 새 BP/인스턴스 거리·개수 설정을 확인하고 회수→먼 구역 왕복→입항 정리→재출항 갱신을 시험한다.
- 기존 배 사격/항해 회귀와 파괴 이벤트1회·기존 비행 포탄 피해를 확인한 뒤 EnemyShipPawn을 구현한다.
- 전체 Editor 빌드·재시작 후 보행과 배 탑승 상태에서 Debug_PrintInventory를 각각 실행한다.
- 빈 인벤토리 안내 및 통 회수 후 수량이 ESC UI와 일치하는지 확인한다.

### 오늘의 기술 정리 (TIL)

- Water의 표시 경계 변화만으로 실제 부력 적용 범위의 정상화를 판단할 수 없다.
- Perforce에서 옛 리비전을 로컬로 받는 단계와 변경을 되돌려 새 리비전으로 제출하는 단계는 서로 다르다.
- 액터의 거리 정리와 회수에 따른 소진은 다르므로 최초 생성 기록·활성 약한 참조·소진 상태를 분리했다.
- 출항은 탑승이나 저장 이벤트가 아니라 모든 항구 겹침 상태가 true→false로 바뀌는 순간으로 판단했다.
- C++ 기본값 수정은 이미 저장된 Blueprint/인스턴스 재정의값을 강제로 바꾸지 않는다.
- 사망 잠금을 콜백보다 먼저 설정하고 필수 정지를 네이티브 구독으로 수행하면 중복 사망과 BP Parent 누락 영향을 줄일 수 있다.
- 현재 조종 Pawn에 두면 도보와 배 조종에서 접근 경로가 달라지는 공통 명령은 GameInstance 등 공통 실행 위치를 검토할 수 있다.
- 데이터 지급 성공과 디버그 명령 호출 실패는 별개의 문제이므로 저장 로그·UI·호출 경로를 비교한다.
